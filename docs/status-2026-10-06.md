## Blank-window isolation and correction

The supplied blank-window screenshot was reproduced with the authenticated diagnostic profile. The page reached `https://discord.com/app`, loaded 352 scripts and 315 stylesheets, but left an empty zero-height application root. The same profile with `--diagnostic-authenticated-no-bridges` rendered the authenticated Friends view with a populated DOM and title `(90) Discord | Friends`. The difference isolates the failure to the partial `DiscordNative` object, not to WebView2 navigation or the persisted profile. The normal shell now keeps both audited bridge groups behind explicit diagnostic modes until their full frontend capability contract is implemented. The rebuilt normal shell launched and Windows reported it responsive.

## New Phase 2 attribution evidence

The authenticated CDP performance window measured almost no JavaScript, layout, or style-recalculation time during idle. CDP process IDs also correlate directly with Windows PIDs for the browser, renderer, GPU, network, and storage roles. The current evidence therefore points to native Chromium/GPU/runtime allocations and process overhead rather than a measured page-level scripting loop. No normal-shell Chromium flags or forced collection behavior has been added.

The latest manual-checkpoint comparison against the contemporaneous official checkpoint measured 54.45% lower summed working set, 69.74% lower private working set, 73.83% lower private bytes, and 92.59% lower total CPU for Track B. A fresh 10-minute simultaneous read-only comparison then measured 43.21% lower summed working set, 63.81% lower private working set, and 72.90% lower private bytes for Track B. The exact authenticated route remains user-confirmed rather than independently machine-verifiable, so these are comparative evidence rather than the final same-route acceptance result. A current blank-profile floor measured 146.69 MiB median private bytes; the loaded-minus-blank delta was approximately 109.63 MiB, of which approximately 100.94 MiB was attributable to the renderer's private bytes. The newer separated-role run measured 120.31 MiB renderer private bytes, 58.20 MiB GPU private bytes, 41.77 MiB WebView2 browser private bytes, and 11.38 MiB native-shell private bytes. Two consecutive current-build 10-minute runs then measured 243.64 MiB median and 244.05 MiB p95 private bytes, keeping the resource target below 250 MiB across 40 samples. See `docs/benchmarks/track-b-contemporaneous-official-comparison-600s-2026-10-06.md` and `docs/benchmarks/track-b-current-settled-10min-paired-2026-10-06.md`.

## Current conclusion

EcoQoS remains a private, background-idle experiment. Stock Discord remains the Track A reference for active use. Track B now has a repeated current-build resource pass showing a large reduction in resident-private memory and CPU. The repository must stay private until a shell passes the same-workload comparison and the required functional checks.

The latest 123.8-second read-only Windows counter capture found a stable seven-process tree, zero sampled GPU-engine utilization, 17.5 MiB median dedicated GPU memory, zero median page-fault rate, and zero median disk I/O. It does not replace the unavailable ETW stack trace and wakeup evidence. The controlled old-versus-current source comparison found no memory increase in the current source relative to the older checkout, but it remains a sequential control rather than a code-only proof. See `docs/benchmarks/track-b-phase2-windows-counters-2026-10-06.md` and `docs/benchmarks/track-b-old-vs-current-source-control-2026-10-06.md`.

The first valid loaded-frontend baseline after bridge isolation measured 706.18 MiB median private bytes, 433.84 MiB median private working set, and 0.226% CPU across eight processes. CDP measured approximately 118.6 MiB live V8 heap and low idle page activity, while the renderer and GPU accounted for approximately 379.3 MiB and 212.3 MiB private bytes. See `docs/benchmarks/track-b-normal-no-bridges-attribution-2026-10-06.md`.

A diagnostic-only no-GPU control reduced private bytes to 489.20 MiB median but reduced private working set by only 19.5 MiB and increased CPU to 0.468%. Hardware acceleration therefore remains enabled in the normal shell. See `docs/benchmarks/track-b-no-gpu-attribution-2026-10-06.md`.

The WebView2 general-autofill control was rejected and reverted. Its short run measured 506.38 MiB median private working set, 705.00 MiB private bytes, and 1.185% CPU, with startup settling still visible.
